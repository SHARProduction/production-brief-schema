# SHAR-proposed production handoff and acceptance guide

Version 0.1.0. Authored working proposal, not an international standard, legal certification or accepted client contract. Apply it by agreement with the producer. This guide reads existing public contracts; it does not create MCP write/submission capabilities.

1. **Prepare inputs.** Run `node example.mjs brief`. The observed `get_brief_requirements` data contract has `locale`, `required`, `optional` and `process`. Use its current required/optional fields as the starting checklist. Record objective, audience, intended channels, launch timing, requested outputs, budget context and rights constraints where applicable. The adjacent completeness checker is a stricter local preparation profile; passing it does not submit or approve a project.
2. **Choose a method explicitly.** Run `node example.mjs methods`. The current response exposes `methods`, `capabilityData`, `relatedServices`, `caveat`. Discuss the returned caveat and method limits, product accuracy and available source material. Choosing AI or CGI is a production decision; the example does not promise quality, savings or feasibility.
3. **Agree the handoff package.** Run `node example.mjs deliverables`. Its observed data contract exposes `serviceId`, `locale`, `deliverables`, `canonicalUrl`. Use those current service deliverables as a conversation starter. Agree actual master versions, duration, aspect ratios, language/subtitle needs, file format and delivery destination in the project brief. Do not interpret this API result as an agreed purchase or rights transfer.
4. **Set acceptance criteria before production.** For each agreed output, record the responsible approver, what they will review, review deadline, revision scope and the evidence needed to accept it. Check visible product/brand accuracy, intended message, technical export, playback, subtitles where agreed, and documented rights/permissions. These are SHAR-proposed checklist dimensions, not extra promises inferred from the API.
5. **Close the handoff.** Compare delivered files against the agreed list, record version identifiers and open issues, and obtain the approver's explicit acceptance through the agreed human workflow. Keep client files and sign-off records private. The public MCP and this client do not upload, send mail, accept projects or store review records.

Record source lineage and retrieval date when using API output. A later source version may change planning information; preserve the actual project agreement separately. Commercial discussion uses the existing [SHAR contact page](https://sharprod.com/contact.html); no data is transferred automatically.

## Предлагаемый SHAR порядок передачи и приёмки

Это рабочее предложение SHAR, а не международный стандарт или юридическая сертификация. ТЗ и условия утверждаются с продюсером.

1. Получите текущие требования командой `brief`; используйте `required`, `optional` и `process` как основу подготовки. Проверка заполненности не отправляет бриф и не утверждает проект.
2. Команда `methods` возвращает сравнение и `caveat`. Обсудите ограничения AI/CGI, точность продукта и доступные материалы, прежде чем выбирать метод.
3. Команда `deliverables` показывает публичные результаты услуги AI-video. Зафиксируйте именно согласованные версии, хронометражи, форматы, языки, субтитры и способ передачи в проектном ТЗ.
4. До производства согласуйте ответственного за приёмку, сроки проверки, объём правок и критерии: изображение продукта/бренда, сообщение, технические файлы и подтверждённые права в пределах проекта.
5. Сверьте переданные файлы с ТЗ, отметьте версии и замечания, получите явное согласование человека. Клиентские материалы и акты приёмки остаются в приватном рабочем контуре.

API даёт публичную информацию и происхождение данных. Он не заменяет договор, смету, согласование прав или фактическую приёмку.
